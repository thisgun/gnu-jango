# 홈·쇼핑몰 초기 로딩 개선

작성일: 2026-10-14

## 적용 내용

- Django에 `/api/v1/home`, `/api/v1/shop/home` 추가. 기존 조회 함수를 재사용해 홈의 게시판·FAQ·댓글과 쇼핑몰의 분류·상품·배너·후기 등을 한 응답으로 전달한다. 개별 API는 그대로 제공한다.
- 브라우저에서 동시에 호출하는 구성 요소들이 진행 중인 요청을 공유한다. 완료된 페이지 응답을 전역에 계속 보관하지 않아 페이지 재방문 시 다시 조회한다. 기존 공개 설정의 60초 캐시는 유지한다.
- 쿠키·인증 헤더가 없는 비로그인 요청의 공통 데이터만 서버에서 30초 캐시한다. 로그인 요청과 쿠키가 있는 요청은 조회 권한을 다시 적용한다. 투표 여부·장바구니는 공통 캐시에 포함하지 않는다.
- 게시글·댓글·파일·FAQ·상품·분류·배너·후기·쿠폰·주문·설정 변경은 DB 커밋 후 캐시 세대를 갱신한다. 샘플 생성·삭제는 묶음당 한 번만 갱신하며, 상품 유형의 `bulk_update` 보정도 명시적으로 무효화한다.
- 운영에서 프로세스별 로컬 캐시를 사용하면 공통 응답 캐시를 우회한다. 여러 Vercel 인스턴스 사이의 변경 사항을 반영하려면 기존 `CACHE_URL`에 공유 DB 또는 Redis 캐시를 사용한다.
- 쇼핑몰·마이페이지 전용 CSS를 해당 레이아웃으로 분리했다. FAQ와 팝업의 HTML 정제 코드를 별도 청크로 분리했고, FAQ를 기다리며 게시글 표시까지 지연되지 않도록 로딩 경계를 추가했다.
- Pretendard 1.3.9의 공통 서브셋 12개를 205,200바이트의 `GnuUI.woff2`로 합쳤다. 글자 모양과 가변 굵기를 유지하고, 나머지 문자는 기존 서브셋으로 표시한다. 변경한 폰트의 이름과 PostScript 접두사를 바꾸고 OFL 라이선스를 소스와 배포물에 포함했다.
- 번들에 포함된 샘플 이미지·로고·OG 이미지에 브라우저 1시간, CDN 1일 캐시를 설정했다. 고정 파일명이므로 `immutable`은 사용하지 않는다. API 응답은 `no-store, private`이며 서비스 워커·매니페스트의 캐시 정책은 유지한다.
- Django용 정적 테마를 다시 생성했다. 현재 배포의 해시 자산을 호환 목록에 유지하고, 이번 작업의 중간 빌드에서만 생성된 불필요한 자산은 제거했다.

## 측정 결과

### 같은 로컬 데이터로 비교

`127.0.0.1:8081`의 변경 전·후 정적 테마를 각각 3회 측정한 중앙값이다. Chromium, 390×844 뷰포트, 다운로드 1.6Mbps, 지연 150ms 설정, CPU 4배 감속, 새 브라우저 캐시를 사용했다. 서버는 가동된 상태다.

**로컬 개발 서버는 자산을 압축하지 않으므로 아래 시간은 Vercel 운영 속도가 아니다.** 같은 조건의 변경 효과를 비교하는 값이며, 실제 기기의 Core Web Vitals나 콜드 스타트를 대표하지 않는다.

| 지표 | 홈 변경 전 → 후 | 쇼핑몰 변경 전 → 후 |
| --- | --- | --- |
| 초기 JSON API 요청 수¹ | 11 → 2 | 14 → 2 |
| FCP | 8.824 → 7.516초 | 8.836 → 7.528초 |
| LCP | 11.108 → 9.012초 (**18.9% 단축**) | 13.940 → 11.420초 (**18.1% 단축**) |
| 초기 JSON 조회 완료 | 10.748 → 8.616초 | 14.203 → 10.461초 |
| 폰트 요청 수 | 9 → 1 | 14 → 3 |
| 폰트 전송량 | 232 → 201KiB | 363 → 253KiB |
| CSS 전송량 | 541 → 417KiB | 541 → 539KiB |

¹ 썸네일 이미지 요청을 제외했다. 홈은 통합 데이터와 소셜 로그인 제공자, 쇼핑몰은 통합 데이터와 장바구니를 조회한다. 이미지·정적 파일 요청은 별도다.

홈의 첫 게시글 표시도 10.866초에서 8.776초로 약 19.2% 단축됐다. FAQ가 나중에 로드되므로 홈의 전체 JavaScript 전송량은 거의 같지만, 첫 표시를 위해 필요한 JavaScript가 줄고 게시글을 먼저 표시한다.

HTML에 선언된 초기 JavaScript 파일을 같은 gzip 설정으로 비교하면 홈 362→298KiB, 쇼핑몰 381→317KiB로 각각 약 64KiB 줄었다. 이 수치는 HTML의 선언 목록 기준이며, 브라우저에서 나중에 요청하는 FAQ 청크까지 포함한 전체 전송량과 구분한다. 쇼핑몰 CSS의 gzip 총량은 86→87KiB로 거의 같고, 분리 효과는 주로 홈에서 나타난다.

새 통합 API의 로컬 응답은 캐시 없이 홈 317ms·쇼핑몰 193ms, 캐시가 있으면 6~17ms였다. 운영 Supabase 네트워크 지연을 포함한 결과는 배포 후 별도로 측정해야 한다.

원시 측정 기록: [page-loading-performance.metrics.json](./page-loading-performance.metrics.json)

### 재측정 방법

```powershell
cd nextjs
node scripts/measure-mobile-pages.mjs http://127.0.0.1:8081 3 "$env:TEMP/gnu-mobile-performance.json"
```

운영 배포 후에는 주소를 `https://gnu-jango-demo.vercel.app`으로 바꿔 측정한다. 변경 전 운영 기록과 비교할 때 DB 데이터, 네트워크, CPU, 캐시 조건을 맞춰야 한다. 관리자 로그인·업로드·샘플 데이터 변경은 이 측정 스크립트가 실행하지 않는다.

## 검증

- Django 회귀 검사 **73개 통과**: 통합 API, 샘플 생성·삭제·유형 보정, 비공개 게시글 권한, 방문자별 투표 상태, 캐시 커밋·롤백, 운영 로컬 캐시 우회, 상품·분류·배너와 정적 이미지.
- Playwright 기존 홈·헤더·상품 상세 검사 **3개 통과**. 헤더 검사에서 모든 `header`를 선택하던 기존 선택자를 주 배너 영역으로 수정했다.
- `npm run typecheck`, `lint`, `check:runtime-config`, `check:design-system`, `check:g5-url-shape`, `check:static-export-guards`, `check:scripts`, `check:file-size` 통과.
- `npm run build:theme`, `check:theme-sync` 통과.
- 3000 Next.js 프론트엔드에서 홈·쇼핑몰 데이터 표시 확인.
- 8081 Django에서 홈·쇼핑몰·상품 상세·비로그인 마이페이지를 데스크톱과 모바일 화면으로 확인. HTTP 200, 가로 넘침 없음, 처리되지 않은 JavaScript 오류 없음.

## 배포 시 확인할 사항

- 새 통합 API와 새 테마 자산은 같은 배포에 포함해야 한다. 프론트엔드만 먼저 배포하면 새 API가 404를 반환한다.
- 샘플 이미지 파일을 같은 이름으로 교체하면 브라우저에는 최대 1시간, CDN에는 설정된 캐시 기간 동안 이전 이미지가 남을 수 있다. 이미지 교체 시 파일명 또는 버전 쿼리를 갱신한다. 샘플 데이터의 추가·삭제 자체는 API 캐시 무효화로 처리한다.
- 서버 측 직접 `QuerySet.update`·`bulk_update`를 사용하는 새 변경 기능에는 `invalidate_page_bootstrap()` 호출이 필요하다. 기존 샘플 유형 보정은 처리했다.
- 이 보고서는 로컬 구현 및 측정 결과를 기록한다. 운영 배포 결과와 확인 내용은 배포 기록에 별도로 남긴다. 운영 개선율과 콜드 스타트는 배포 후 확인한다.
