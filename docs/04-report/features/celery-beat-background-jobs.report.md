# Celery Beat·DB outbox 구현 보고

작성일: 2026-10-24

## 구현

- 기존 9개 유지보수 명령을 `CELERY_BEAT_SCHEDULE`에 등록했다. 실제 명령 구현과 수동 실행 호환 경로를 재사용한다.
- `BackgroundJob` 모델과 `core.0015_backgroundjob` 마이그레이션을 추가했다. 상태·작업명·시도 횟수·실행 임대·다음 처리 시각·최종 실패 코드를 저장한다.
- 요청은 DB 대기열만 기록하고 Beat가 UUID를 Redis로 전달한다. 메시지 유실은 재전달하고 중복 전달은 DB의 조건부 claim으로 건너뛴다. 정기 작업은 활성 키로 겹치는 실행을 막는다.
- 재시도와 jitter, 270/300초 soft/hard timeout, 360초 임대 복구, 최종 실패 큐를 구성했다. 메일·SMS의 접수 여부 불명 건은 자동 재송신하지 않는다.
- 메일 기본 backend와 캠페인 등록, 주문·회원 SMS, 인증 완료한 서버 결제 웹훅을 연결했다. 기존 PG 조회·금액·거래 확인과 결제 상태 변경 로직을 유지한다.
- 이미지 원본을 비공개 outbox에 보관하고 공개 경로에는 작은 임시 이미지를 저장한다. 실제 메타데이터 제거·썸네일 생성은 media 큐에서 수행한다. 요청에 필요한 파일·이미지 검증은 유지한다.
- 최고 관리자용 실패 큐와 재처리 명령, 보관 기간 정리, PostgreSQL RLS/API 역할 권한 제거를 추가했다. 작업 원문은 관리자와 Celery/Flower 인자에 노출하지 않는다.
- 일반 작업자·이미지 작업자·단일 Beat·선택적 Flower의 Docker 구성을 추가했다. Flower는 인증·읽기 전용·localhost 노출을 사용한다. Redis는 AOF 볼륨을 사용한다.
- 사이트마다 Redis broker/result 키를 분리하며, 웹·작업자의 설정 일치와 전환·복구 절차를 문서화했다.

## 확인한 내용

- 변경·신규 Python 파일 31개의 구문 분석 통과.
- `BACKGROUND_JOBS_ENABLED=False`와 `True` 각각 Django 시스템 검사 통과(기존 silenced 항목 1개).
- 기본 Compose + monitoring, realtime overlay + monitoring Compose 구성 검사 통과.
- `git diff --check` 통과.

## 후속 실행 검증 (2026-10-24)

사용자의 후속 진행 요청에 따라 외부 통신이 차단된 Docker 내부 네트워크에 PostgreSQL 16, Redis 7, Linux prefork 작업자, Beat와 Flower를 별도로 실행했다. 기존 개발 서버와 Redis, 실제 `db.sqlite3`, Supabase 및 공개 배포는 변경하지 않았다. 모든 발송 대상·계정·주문은 테스트용이다.

### 자동 테스트

- `core/test_background_jobs.py`에 회귀 테스트 36개를 추가했다.
- 새 테스트 36개와 기존 가상계좌·SMS·썸네일·이미지 개인정보·쇼핑몰 메일·배포 설정 테스트 151개를 **병렬 옵션 없이** 실행하여 PostgreSQL에서 187개 모두 통과했다(137.929초).
- SQLite에서도 새 테스트 36개를 실행하여 34개 통과, PostgreSQL 전용 동시 claim·RLS 검사 2개는 제외했다(6.946초). 테스트 DB 생성 과정에서 SQLite 마이그레이션도 적용했다.
- DB 트랜잭션 롤백, UUID만 브로커에 전달, 중복·동시 claim, 재시도 간격·시도 한도, 임대 복구, 실패 큐 재처리, 보관 기간 정리를 확인했다.
- 메일의 MIME·첨부·숨은 참조, SMTP 응답·연결 실패 분류, 캠페인 집계, SMS 자식 작업 중복 방지, 웹훅 인증·금액 검증·멱등성, 이미지 삭제 우선 처리와 EXIF 제거를 확인했다.
- PostgreSQL에서 outbox RLS 활성화와 `anon`·`authenticated`의 SELECT 권한 부재를 확인했다. 새 빈 DB에 전체 마이그레이션을 적용했다.
- 변경 Python 파일의 Ruff 검사와 `git diff --check`를 통과했다.

### 실제 프로세스 검증

| 시나리오 | 결과 |
|---|---|
| 로컬 SMTP 수신까지 처리, 동일 UUID 두 번 추가 전달 | 한 번만 발송, 성공 후 DB 원문 제거 |
| 로컬 iCode 프로토콜 수신 서버까지 SMS 처리 | 정상 접수·완료 |
| 인증된 Toss 웹훅 → 로컬 PG 조회 → 주문 반영 | 정상 처리, 웹훅 비밀은 작업 payload에 저장하지 않음 |
| EXIF 사진 업로드 → 안전한 임시 이미지 → 회전·메타데이터 제거 → WebP 썸네일 | 정상 처리 |
| Beat의 주문 포인트·보관 기간 정리 및 outbox 전달 | 정기 실행·완료 확인 |
| Flower 접근 | 미인증 401, 인증 후 200 |
| soft timeout | 대기 상태로 복구 후 다음 시도 성공 |
| hard timeout으로 작업자 자식 프로세스 종료 | DB 임대 만료 복구 후 다음 시도 성공 |
| SMTP가 수신한 뒤 작업자 종료 | `delivery_uncertain`, 일반 재처리 거부, 자동 중복 발송 없음 |
| 전용 Redis 중단 | 요청의 DB 접수 유지, 전달 실패 후 대기 상태 유지 |
| 전용 Redis의 메시지 제거·재시작 | 전달 임대 만료 후 DB에서 재발행, 각각 한 번만 발송 |

시간 제한 장애 시험은 테스트 작업자만 soft 1초·hard 2초로 줄였고 DB 임대를 명시적으로 만료시켜 복구 경로를 실행했다. 운영 기본값 270/300/360초를 실제 시간만큼 기다린 시험은 아니다. Redis 중단 시 한 번의 전달 시도는 약 6.2초 안에 실패하고 DB 기록을 보존했다.

실행 중 작성한 수신 서버·장애 주입 도구와 합성 데이터 기록은 저장소 밖 `E:\gnu-jango\local-notes\background-jobs-20261024\`에 보관했다. 저장소에는 실제 동작을 보호하는 회귀 테스트를 추가했다. 실제 SMTP/iCode/Toss 사업자의 접수·정산, S3 저장소, 장시간 부하와 운영 전환은 이번 검증 범위에 포함하지 않는다.

### 발견하여 수정한 문제

실패 큐의 `replay()`가 호출자가 전달한 모델 인스턴스의 과거 상태를 신뢰했다. 관리자 조회 뒤 다른 실행의 발송 결과가 `delivery_uncertain`으로 바뀌거나 보관 기간 정리로 payload가 제거되어도 재처리를 등록할 수 있었다. 이제 트랜잭션 안에서 현재 행을 잠근 뒤 상태·실패 코드·원문 존재 여부를 다시 검사한다. 두 경쟁 상황을 먼저 실패하는 테스트로 재현하고 수정 후 통과를 확인했다.

## 운영 반영에 필요한 작업

1. 백업 후 새 마이그레이션을 적용한다.
2. 웹과 같은 DB·공유 미디어·외부 발송 설정을 가진 작업자와 Beat 하나를 준비한다.
3. `BACKGROUND_JOBS_ENABLED=True`를 웹·작업자에 함께 적용하고 일반·이미지 큐를 소비하게 한다.
4. 기존 cron/watch 운영과 중복되지 않게 전환하고 실제 대기열 감소·성공·실패 상태를 확인한다.
5. Flower 인증 정보를 저장소 밖에 설정하고 필요할 때 monitoring 프로필을 실행한다.

기존 설치에서는 기본값 `False`를 유지하며 Docker Compose에서는 새 모드를 기본으로 사용한다. 이번 작업에서 공개 데모·핸드북 설정 변경, 운영 DB 마이그레이션, 상시 작업자 배포는 수행하지 않았다.

## 외부 작업자 배포 준비 (2026-10-24)

- 기존 검증·재처리 수정은 `f43bf339e`로 커밋했다.
- `docker-compose.background.yml`과 저장소 밖 환경 파일용 템플릿을 추가했다. 기존 Vercel·Supabase 사이트의 DB·S3를 이용하며 새 웹·DB 서비스를 생성하지 않는다. 사이트별 Compose 프로젝트와 Redis·Beat 볼륨을 분리한다.
- 외부 작업자 전용 entrypoint는 PostgreSQL·S3 설정을 요구하고, 호환 설정 및 `migrate --check` 확인 후 시작한다. 누락된 마이그레이션을 자동 적용하지 않는다.
- 기본 Compose의 웹·작업자·Beat 환경을 공통 매핑으로 합쳤다. 기존에 누락된 SMS·PG·S3 설정을 함께 전달한다. env 파일의 보간만으로 컨테이너 환경 변수가 전달된다고 가정하지 않는다.
- Vercel 운영 설정의 S3 검사가 비동기 저장소 wrapper를 잘못 거부하던 문제를 수정했다. 실제 원본 저장소가 S3인지 검사하며 로컬 저장소 거부는 유지한다.
- `.dockerignore`에서 로컬 worktree·도구 설정·가상환경·SQLite를 제외했다. 최종 이미지 안에 `.wt-docs-ask`, `.serena`, `.claude`, 가상환경과 `db.sqlite3`가 없는지 확인했다.
- 합성 설정으로 기본 Compose, realtime + monitoring, 독립 작업자 + monitoring 구성을 확인했다. 기본 Compose의 웹·각 작업자에 공급자 설정이 동일하게 전달되며 독립 구성에는 웹·DB·공개 Redis 포트가 없는 것을 확인했다.
- 운영 설정은 Vercel 비동기 켜짐·꺼짐 각각 로딩 및 호환 검사를 통과했고, Vercel 로컬 미디어 설정은 계속 거부했다.
- 최종 Docker 이미지 빌드, 비특권 사용자 실행, `$`·`#`를 포함한 합성 키의 실제 컨테이너 전달, entrypoint 실행 권한·셸 구문, DB 주소 미설정 시 연결 전에 중단하는 동작을 확인했다. 이번 준비 단계에서 자동 테스트를 추가·재실행하지는 않았다.

실제 서버 주소·SSH 사용자·대상 사이트가 제공되지 않아 원격 배포와 사업자 테스트키 발송·결제 검증은 실행하지 않았다. 기존 개발 서버와 운영 DB·환경 변수는 유지한다. 구체적인 명령과 전환·중단 순서는 [외부 작업자 배포 안내](../../04-deploy/external-background-workers.md)에 기록했다.
