# 검색 신뢰성 보강 결과

작성일: 2026-10-21

## 반영 상태

로컬 구현과 격리 DB 검사 결과다. 커밋·푸시·운영 배포 및 운영 DB 마이그레이션은 수행하지 않았다. 8081 서버, 운영 DB, Supabase 환경과 기존 사용자 작업 파일은 변경하지 않았다. UI/테마 소스 변경과 테마 재빌드는 없다.

## 구현

| 요구사항 | 변경 |
|---|---|
| R1 본문 권한 | 공통 `post_body_match`로 혼합/대체 검색에도 비밀글·읽기 등급·읽기 포인트 적용 |
| R2 부분 검색 | 기존 API의 단일 한글·ASCII 부분 문자열 유지, 통합 API의 ASCII 접두 검색과 BM25 빈도 일치 |
| R3 저장·복구 | 원본 저장 트랜잭션, 색인 내부 savepoint, 실패 시 durable retry, 백오프·중복 실행 직렬화·삭제 정리 |
| R4 누락 검사 | 동일 SQL 스냅샷의 원본/색인 지문 비교, PK 커서, 명시적 enqueue, 순환 점검 |
| R5 규모 | 로컬 일회용 PostgreSQL 1만 페이지·100개 합성 질문·4개 동시 조회와 10회 수정 |
| R6 감시 | 상태/누락/대기/지연 점검, 기존 예약 작업 연결, 질문·본문을 제외한 요청 로그와 Server-Timing |
| R7 배포 검사 | 성공한 main CI 뒤 커밋 일치 대기 및 공개 20문항 검사 워크플로 작성 |

PostgreSQL에는 저장 벡터와 GIN 인덱스를 적용하고, BM25 후보의 질문 관련 빈도·토큰 길이만 SQL에서 추출한다. 원시 후보 본문 토큰을 모두 Python으로 전송하던 비용을 줄였다. 빈도 추출과 Python BM25의 접두 빈도·길이 일치도 검사했다.

## 검증

| 검사 | 결과 |
|---|---|
| SQLite 검색/권한/게시판·상품 검색/예약 작업·cron | 74개 성공, 3개 PostgreSQL 전용 skip |
| PostgreSQL 16 검색·게시판 목록·예약 작업 회귀 | 96개 성공, 1개 SQLite 전용 skip |
| PostgreSQL 보강분 | 빈도/길이·커서 순환·복구·메트릭·배포 대기 검사 포함 |
| 기존 데이터 마이그레이션 | 토큰이 있는 0004 DB → 0007, 벡터/GIN 확인, 0005 왕복 적용 및 원본 보존 확인. anon 기본 SELECT/INSERT 권한을 부여한 실험에서도 새 재시도 테이블의 권한 회수 확인 |
| Ruff·migration drift·YAML 구조·diff whitespace | 통과 |
| 전체 프로젝트 SQLite 검사 | 2,354개 성공, 9개 skip(테스트 전용 해시 설정), 749.620초 |
| 최종 SQLite 보강 검사 | 14개 성공, 1개 PostgreSQL 전용 skip. 재시도 처리 순서·최종 감사·라우팅 포함 |

초기 예약 작업 검사의 빈 DB는 색인 초기화를 선행하도록 수정했다. 접두 검색이 성공하게 된 기존 오타 예제는 단어 내부 오타로 바꾸고 기존 예제의 비유사 검색 성공도 검사한다. 최초 SQLite 실행의 잘못된 테스트 클래스 이름과 별도 DB 테스트의 개발용 SECRET_KEY 조건도 바로잡았다. 중간 실패 로그를 최종 성공 수에 포함하지 않았다.

첫 전체 검사 2,354건에서는 기존 작성자의 자기 비밀글 본문 검색이 차단된 회귀 1건을 발견했다. 기존 테스트를 유지하고 실제 열람 권한을 통과하는 비밀 본문의 리터럴 검색을 복원했다. 비밀 본문을 공유 색인에 넣지 않으며 통합 검색 정책은 유지한다. 수정 후 관련 PostgreSQL 96건과 별도 SQLite 보강 검사를 통과했고, 전체 2,354건도 다시 실행해 성공했다.

전체 SQLite 실행기는 격리 DB·개발용 키를 사용하며 테스트 프로세스에서만 `PBKDF2PasswordHasher.iterations=1000`으로 해시 비용을 줄인다. 비밀번호 알고리즘·검증 방식과 운영 설정은 변경하지 않았다. 기본 비용으로 시작한 중간 전체 실행은 중단했으며 성공 결과에 포함하지 않는다. PostgreSQL 관련 회귀는 기본 해시 설정으로 실행했다.

## 1만 건 측정

20개 합성 식별자에 5가지 질문 변형을 적용한 100문항에서 세 단계 모두 Top-3 100/100이었다. 모든 1만 페이지가 맞는 넓은 질문은 후보 200건으로 제한했다. 네 개 조회 작업과 별도 작성 작업을 함께 실행한 뒤 색인 대기·지문 불일치는 0이었다.

| 단계 | 순차 평균 / p95 | 동시 평균 / p95 |
|---|---:|---:|
| 저장 벡터 전 | 4469.56 / 5585.64ms | 4160.39 / 5242.79ms |
| 저장 벡터 적용 | 635.12 / 645.87ms | 2122.17 / 3071.62ms |
| 질문 빈도/길이만 전송 | 800.30 / 829.50ms | 1068.52 / 1338.29ms |

마지막 단계는 설정한 순차/동시 p95 2000ms 기준을 통과했다. 저장 벡터만 적용한 중간 단계는 동시 p95 기준에서 실패했으며 최종 단계에 빈도 전송 개선을 추가했다.

Windows의 로컬 PostgreSQL 16 컨테이너와 Python 3.14.6 관리 함수 측정이다. 각 단계의 순차 표본은 3개, 동시 표본은 12개로 작고 같은 컴퓨터의 다른 검사 부하도 있었다. 실제 네트워크 HTTP, 여러 서버의 부하, 콜드 스타트 성능은 별도 측정해야 한다. 합성 접두 문제의 100%가 실제 고객의 한국어 질문 정확도 100%를 뜻하지 않는다. 기존 운영 정답표 20문항은 이번 변경을 배포한 뒤 다시 측정해야 한다.

## 운영 반영과 한계

- `site_search.0005`~`0007`을 먼저 적용하고 새 코드를 배포한다. 열/인덱스 생성의 잠금·추가 디스크와 SQLite 임시 공간을 확인한다.
- 기존 부분 문자열 검색에는 원문 조회 비용이 있다. 통합 검색의 후보 제한 200건과 4096개 본문 토큰 제한은 유지한다.
- bulk update/import 후에는 커서로 전체 원본 감사를 수행한다. 주기 점검은 종류별 기본 25개씩 순환하므로 전체 감사 주기를 계산해야 한다.
- GitHub 워크플로는 main 반영 뒤 실행된다. Vercel 시스템 커밋 변수와 Actions 실패 알림을 확인한다. 이번 작업에서 클라우드 자동 검사 실행을 주장하지 않는다.
- 테스트용 PostgreSQL 컨테이너·DB·익명 볼륨은 소유 이름/라벨·호스트 bind 부재를 확인한 뒤 정리했다. 다른 서비스의 컨테이너·가상환경은 보존했다.
