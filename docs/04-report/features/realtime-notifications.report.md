# 실시간 알림 구현 결과

초기 구현: 2026-10-21 · 후속 개선 및 실제 연결 확인: 2026-10-22

## 구현

- `gnu_jango/notifications/`: 댓글·수신 쪽지·주문 변경을 기존 알림 모델에 연결했다.
  본인 알림/중복 수신자를 제외하고, 이전 그누보드에서 가져온 게시글은 공개 글 번호로 연결한다.
- 원본 DB 커밋 뒤 알림 생성 작업을 기록한다. 알림 생성 실패는 `NotificationWork`에 남겨 재시도하며 이미 확정한 결제·댓글을 되돌리지 않는다.
- 요청 중에는 Redis 전송을 기다리지 않는다. 전용 `process_notifications --apply --watch` 작업자가 개인 그룹 변경 신호를 전송한다.
- 30초 일회용 접속권, Origin 제한, 수신 크기 제한, 인증 시간 제한, 계정/세션 재검사와 연결 갱신을 구현했다.
- 알림 벨을 기본 테마의 커뮤니티·쇼핑몰과 핸드북에 연결했다. 접속권 요청은 CSRF·토큰 갱신 대기를 포함하여 8초 뒤 취소·재시도한다.
- 관리자 공지 요청 ID를 `NotificationAnnouncement`에 저장하고 알림 생성과 함께 커밋한다. 캐시 초기화·동시 요청에도 중복 발송을 막는다.
- 자료 가져오기·샘플 생성은 요청별 ContextVar로 자동 알림을 억제한다. 동시 회원 요청의 알림은 계속 동작한다.
- 실제 연결 확인에서 Redis 읽기 제한 1초가 Channels의 정상적인 5초 대기보다 짧은 문제를 발견해 10초로 수정했다.
- 채널 계층 예외에서도 연결 감시 작업과 개인 그룹을 정리한다. 모바일 팝오버는 화면 안에 배치하고 Esc로 닫힌다.
- `core.0013`~`0014`, 선택 설치 requirements, 알림 작업자와 Docker `realtime` 프로필을 제공한다.
- 기본값은 REST 유지다. Preview의 소켓은 강제로 끄며, Expo 앱이 없어 모바일 OS 푸시는 추가하지 않았다.

표의 Django/부분 검사 수는 서로 겹치므로 합산하지 않는다. 전체 회귀 검사는 외부 검증 실행기에서만 PBKDF2 반복 수를 낮춰 실행했고, 운영 비밀번호 해시 설정은 변경하지 않았다.

실제 전송 확인은 임시 PostgreSQL 16·Redis 7 컨테이너와 임의 포트 Uvicorn을 사용했다.
HTTP 접속권 발급부터 실제 TCP WebSocket 연결까지 실행해 사용자별 격리, 위조·재사용·만료 접속권, 잘못된 Origin, 인증 버전 폐기, 재접속과 유휴 연결을 확인했다.
Redis 장애는 접속 불가능한 로컬 엔드포인트로 전송 실패를 만들고, 정상 Redis 설정으로 복원해 대기 작업이 실제 연결에 전달되는지 확인했다.
실제 PG 업체와는 통신하지 않았다. 운영 TLS/WSS·Vercel 배포와 Docker 이미지 전체 빌드는 이번 확인 범위가 아니다.

실제 기본 테마는 별도 빌드 DB와 로컬 API에서 확인했다. 320px 화면의 목록 범위는 x=12, width=296이며 Esc 닫힘과 콘솔 오류 없음도 확인했다.
CI에는 전용 Redis와 알림 회귀 검사를 추가했다. GitHub CI 실행 결과를 확인한 것은 아니며 로컬 실행 결과다.

Python 점검은 실제 `db.sqlite3` 대신 기존 외부 작업용 SQLite 설정으로 실행했다.
선택 패키지는 로컬 `.venv314`에 설치했다: Channels 4.3.2, channels-redis 4.3.0, Uvicorn 0.49.0.
초기 구현에서는 정적 점검까지만 수행했으며, 이후 요청에 따라 위의 회귀·실제 연결 확인을 추가했다.

## 테마 생성 시 주의한 점

초기 빌드에서는 로컬 PHP API의 테스트 게시판을 읽는 문제가 있어 오프라인으로 다시 생성했다.
이번 최종 빌드는 CI와 동일하게 **별도 SQLite DB에 `ensure_handbook_samples --stable-dates`로 준비한 8권·49장**만 사용했다.
고정된 핸드북 RSS 스냅샷도 다시 포함했다. 실제 사용자 DB나 PHP 데이터는 빌드에 사용하지 않았다.

## 운영 반영 상태

구현 당시에는 운영 환경을 변경하지 않았으며, 2026-10-22 배포 요청으로 검색 신뢰성 작업과 함께 PR #53에 커밋·푸시했다.
최신 main의 YoungCart·결제 작업을 통합하고 두 테마를 다시 생성했다. 통합 후 검색·알림·결제 회귀 검사 247개가 통과했다(1개 건너뜀).

두 Supabase 프로젝트의 `public` 및 `g5_preview` 스키마를 저장소 밖에 `pg_dump`로 백업하고 아카이브 목록을 확인했다.
두 운영 DB와 두 Preview 스키마에 `core.0013`~`0014`, `site_search.0005`~`0007` 적용을 완료했다.
네 환경 모두 미적용 마이그레이션이 없고, 저장 벡터 열 4개·GIN 색인 4개와 내부 작업 테이블의 공개 역할 접근 차단을 확인했다.
운영 검색 상태 점검에서 색인/원본 불일치와 재시도 대기 건이 없었다.

이 기록 시점에는 보호된 main의 필수 CI 검사를 진행 중이다. 두 Vercel Preview는 READY이며 데모 Preview 상태 API에서 새 커밋을 확인했다.
첫 Docker smoke에서 이름 없는 PostgreSQL 설정으로 생성 열 기능 검사를 할 수 없어 실패했으며, CI 전용 인메모리 SQLite 설정을 명시하도록 보완했다.
개발 서버 8081과 실제 로컬 DB 및 루트 Vercel 프로젝트 연결은 유지했다.

배포 시 먼저 DB 백업과 마이그레이션 계획을 확인해야 한다.
WebSocket을 사용하려면 선택 패키지, ASGI 실행, **알림 작업자**, Redis, HTTPS/WSS 및 허용 Origin 설정이 필요하다.
운영 반영 절차는 [운영 가이드](../../04-deploy/realtime-notifications.md)를 따른다.
Vercel은 현재 WSGI 진입점을 사용하므로 이번 코드만 올려서는 실시간 기능이 켜지지 않는다.

원본 커밋과 대기열 최초 기록 사이에 프로세스가 종료되거나 대기열 자체가 쓰기 불능이면 그 이벤트의 영속 보관까지 보장하지 않는다.
이 경우 `notification_event_enqueue_failed` 로그를 확인해야 한다. 저장된 대기 작업의 재시도와 원본 결제 보존은 검사했다.
