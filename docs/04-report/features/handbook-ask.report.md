# 매뉴얼 질문 검색 구현 보고서

## 구현 범위

- 핸드북 본문을 문단 단위로 색인하고 한국어 2-gram + BM25로 질문과 관련된 장을 검색합니다. Kiwi 형태소 분석기는 선택 설치로 지원하며, 설치가 없거나 로드되지 않으면 기본 분석 방식으로 자동 전환합니다.
- 결과에는 책·분류·장·절, 해당 문단의 짧은 발췌, 질문어 강조 위치, 바로 이동할 수 있는 문단 앵커를 담습니다. 한 장의 문단이 결과 목록을 여러 자리 차지하지 않도록 장별로 결과를 합칩니다.
- 핸드북 검색 창에 질문 검색을 추가했습니다. 기본 검색과 질문 검색을 함께 보여주고, 질문 결과에는 로딩·오류·결과 없음 상태를 표시합니다. 작은 화면에서도 결과 목록을 사용할 수 있습니다.
- 검색 인덱스는 파일로 저장하지 않고 프로세스 메모리에 보관합니다. 데이터 변경 신호와 내용 지문·공유 캐시 리비전으로 재색인을 감지합니다.
- 선택 기능인 문장 답변은 운영자가 Django 환경 변수로 OpenAI 호환 로컬 모델을 지정한 경우에만 동작합니다. 요청자가 모델 주소를 넘길 수 없으며, 검색 권한을 통과한 문단만 프롬프트에 전달합니다. 출처 번호가 유효하지 않거나 모델이 응답하지 않으면 문장 답변 없이 검색 결과만 보여줍니다.
- 의미 검색(B)은 구현하지 않았습니다. 설계 제안은 아래에만 기록했습니다.

## 접근 권한과 개인정보

기존 통합 검색의 `_searchable_boards`와 `_excerpt_post_ids` 규칙을 재사용합니다. 목록 권한이 없는 게시판과 읽을 수 없는 글은 검색 후보에서 빠집니다. 비밀글은 관리자에게도 질문 검색 결과나 모델 프롬프트에 포함하지 않습니다. 검색 API는 분당 30회로 제한합니다.

## 품질 및 성능 확인

18개 질문으로 샘플 매뉴얼의 기대 장을 확인했습니다. 테스트 데이터베이스는 임시 SQLite 파일을 사용했습니다.

| 확인 항목 | 결과 |
| --- | ---: |
| hit@1 | 8/18 (44.4%) |
| hit@3 | 18/18 (100%) |
| 색인 생성이 포함된 첫 검색 | 43.9 ms |
| 이후 검색의 중앙값 | 9.1 ms |

시간은 Windows 개발 환경의 Python 3.14·SQLite, 샘플 매뉴얼에서 측정한 값이며 Vercel 성능을 의미하지 않습니다. 실제 트래픽·운영 DB에서의 색인 크기와 콜드 스타트는 별도 측정이 필요합니다.

확인 명령과 결과:

- `manage.py check`: 통과
- `manage.py test gnu_jango.docs_search`: 13개 통과
- `manage.py test`: 2,123개 통과, 기존 스킵 6개, 실패 0개 (직렬 실행)
- `npm run typecheck`, `npm run lint`: 통과
- `npm run build:theme:handbook`: handbook 템플릿 및 정적 자산 604개 동기화, 이전 브라우저용 유지 자산 104개 보존
- Playwright 질문 UI·앵커 검사: 3개 통과 (데스크톱, 390px 모바일, Python/TypeScript 앵커 일치)
- Ollama에 연결한 실제 생성 응답은 실행하지 않았습니다. 응답 형식·출처·시간 초과 처리는 모의 응답으로 검증했습니다.

## 형태소 분석기 선택 근거

현재 필수 기능은 외부 모델이나 새 검색 서비스를 요구하지 않아 Vercel과 일반 Django 서버에서 같은 2-gram·BM25 경로로 사용할 수 있습니다. 형태소 분석이 필요한 VPS에는 `requirements-docs-morphology.txt`를 선택 설치할 수 있습니다. 해당 패키지는 프로젝트 환경에서 측정한 설치 후 크기 약 213 MB, 첫 모델 로드 약 2.7초였기 때문에 기본 의존성에 포함하지 않았습니다. 패키지와 모델은 별도 배포물입니다. [kiwipiepy 패키지](https://pypi.org/project/kiwipiepy/), [kiwipiepy 모델 패키지](https://pypi.org/project/kiwipiepy-model/)

## 보류한 의미 검색(B) 설계

1. 같은 매뉴얼 문단과 질문 18개를 사용해 후보 임베딩 모델을 먼저 비교합니다. `multilingual-e5-small`은 검색 질문에 `query:`, 매뉴얼 문단에 `passage:` 접두어를 사용하는 비대칭 검색 규칙을 안내합니다. [모델 카드](https://huggingface.co/intfloat/multilingual-e5-small)
2. 임베딩을 Django 요청마다 생성하지 말고 별도 관리 명령 또는 작업자가 생성합니다. 저장 행에는 게시판 ID, 글 ID, 문단 앵커, 콘텐츠 해시, 모델 이름과 버전을 기록해 변경 문단만 다시 만들 수 있게 합니다.
3. 현재 DB가 PostgreSQL/Supabase인 배포에서는 `pgvector`의 벡터 열과 HNSW 인덱스를 후보로 삼습니다. Supabase 문서는 pgvector의 벡터 저장과 HNSW·IVFFlat 인덱스를 설명하고, HNSW를 일반적인 시작 선택으로 권장합니다. 실제 적용 전에 사용 중인 Supabase 플랜과 확장 버전을 확인합니다. [Supabase pgvector 안내](https://supabase.com/docs/guides/database/extensions/pgvector), [벡터 인덱스 안내](https://supabase.com/docs/guides/ai/vector-indexes)
4. 검색 시에는 벡터 결과와 BM25 결과를 합치는 하이브리드 검색을 비교합니다. 후보 병합은 RRF(Reciprocal Rank Fusion)처럼 순위를 결합하는 방식으로 시작하고, 기존 `_searchable_boards`·`_excerpt_post_ids` 권한 검사를 통과하지 않은 후보는 제거합니다. 권한 검사는 검색 뒤 결과를 숨기는 용도로만 쓰지 말고 DB 쿼리에서 가능한 한 먼저 적용해야 합니다.
5. 합격 기준은 같은 18문항에서 hit@3 80% 이상을 유지하면서, BM25 기준보다 향상되는지 비교하는 것입니다. 질문 표현을 바꾼 추가 사례와 비공개·레벨 제한 문서의 누출 검사를 더한 뒤 모델·저장소·운영비를 결정합니다.

현재 검색 기능은 Vercel 함수 안에서 외부 임베딩 모델을 실행하지 않습니다. Vercel은 Python 함수 번들의 기본 압축 해제 크기를 500 MB로 제한하고 최대 함수 크기를 별도로 설명하므로, 모델 파일을 번들에 넣는 안은 실제 번들 크기·콜드 스타트·CPU 시간을 확인한 뒤에만 선택해야 합니다. 대안은 별도 임베딩 작업자에서 벡터를 생성하고 Django가 DB의 벡터 검색 결과를 사용하는 구조입니다. [Vercel 함수 제한](https://vercel.com/docs/functions/limitations)

이 설계는 구현 승인 전 검토안입니다. 모델과 임베딩 저장소는 아직 추가하지 않았습니다.
