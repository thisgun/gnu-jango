# Celery Beat와 백그라운드 작업 정리 계획 / PRD

작성일: 2026-10-24

## 목적

요청 처리 시간이 외부 메일·SMS 서버, 결제 웹훅 처리와 이미지 변환 시간에 좌우되지 않게 한다. 기존 정기 명령을 재사용하면서 Beat에 실행 주기를 모으고, 실패한 작업을 운영자가 확인할 수 있게 한다.

## 기능 요구사항

1. `CELERY_BEAT_SCHEDULE`에 9개 유지보수 명령과 outbox 전달·보관 기간 정리를 등록한다.
2. 웹 요청은 DB outbox만 기록한다. DB와 작업 등록이 같은 트랜잭션에 포함된 경우 함께 커밋·롤백된다. 요청에서 Redis 연결 또는 eager 실행으로 우회하지 않는다.
3. 메일, 주문·회원 SMS, 서버 결제 웹훅, 썸네일·메타데이터 변환을 별도 작업자가 처리한다.
4. DB에 상태, 시도 횟수, 다음 시각, 작업 임대, 최종 실패 코드가 남는다. 원문·수신자·비밀값은 Celery 인자와 Flower에 보내지 않는다.
5. 최대 5회 시도, 지수 백오프와 jitter, soft/hard timeout, 작업자 중단 후 복구를 적용한다.
6. SMTP의 일시적 거부처럼 미전송이 확인된 경우에만 메시지를 자동 재시도한다. 발송 결과가 불명확하면 `delivery_uncertain`으로 중단한다. 운영자의 확인 없는 중복 발송은 피한다.
7. 관리자 실패 큐와 명령에서 재처리한다. 원문은 관리자에 표시하지 않고 성공 시 즉시 지우며, 최종 실패 원문은 7일 뒤 지운다.
8. 결제 웹훅은 요청에서 기존 인증·서명·secret 검증을 마치고 접수한다. Toss 입금 처리 시 실제 PG 조회와 금액·주문·거래 검증을 유지한다. 고객 결제 승인·반환 흐름은 별도 계약을 유지한다.
9. 이미지 원본은 처리 대기 중 공개하지 않는다. 안전한 임시 이미지와 비공개 outbox 원본을 사용하며, 최종 저장 전에 메타데이터를 제거한다. 삭제한 파일은 지연 작업이 복원하지 않는다.
10. Flower는 선택 설치, 읽기 전용, Basic 인증, 호스트 loopback 바인딩으로 제공한다.

## 운영 요구사항

- Beat는 같은 사이트에 하나만 실행한다. 같은 DB를 사용하는 앱과 작업자는 동일한 설정·메일러·스토리지를 사용한다.
- 일반 작업자와 이미지 작업자는 서로 다른 큐를 소비한다.
- VPS Docker 구성은 웹 마이그레이션과 준비 완료 후 작업자를 시작한다.
- 기존 설치는 `BACKGROUND_JOBS_ENABLED=False`를 기본값으로 유지한다. 실제 워커와 Beat를 준비한 뒤 켠다. Docker Compose는 새 구성을 기본으로 켠다.
- Vercel의 웹 함수나 무료 PythonAnywhere 웹 프로세스 안에서 상주 프로세스를 시작하지 않는다. 외부 작업자를 준비하거나 기존 실행 모드를 유지한다.

## 완료 기준

- 새 모드에서 요청은 발송·PG 재조회·이미지 재인코딩을 수행하지 않는다.
- Redis 전달 실패나 메시지 유실 시 DB 대기 기록이 남고 다시 전달된다.
- 중복 전달은 DB 조건부 claim으로 실행자를 하나만 선택한다.
- 최종 실패와 발송 결과 불명 상태는 운영자가 식별하고 재처리 여부를 결정할 수 있다.
- 사용법·전환·복구·제약을 운영 문서에 남긴다.

## 이번 작업의 확인 범위

Python 구문 확인, 기능 활성화/비활성화 각각의 Django 시스템 검사, Docker Compose 구성 검사를 수행한다. 자동 기능 테스트·부하 테스트·실제 PG/메일/SMS 호출은 별도 요청 전에는 수행하지 않는다. 공개 서비스의 마이그레이션·설정 변경·작업자 가동은 배포 단계에서 진행한다.
