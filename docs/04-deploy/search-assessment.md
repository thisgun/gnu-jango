# 검색 정확도와 속도 점검

현재 공개된 데모 자료로 정답표를 만들고, 검색을 바꿀 때 같은 질문을 다시 실행한다. 이 검사는 소량의 등록 자료에 대한 회귀 점검이다. 실제 고객 질문이나 대규모 동시 접속 부하를 대신하지 않는다.

## 1. 정답표 준비

기본 정답표는 `scripts/data/search-evaluation.json`이다. 핸드북 12문항, 일반 게시글 4문항, 상품 4문항으로 구성된다. 각 문항은 검색어와 정답의 자료 종류·제목·게시판을 명시한다. 결과를 본 뒤 정답을 바꿔 통과율을 높이지 않는다.

자신의 사이트에서는 `sites`의 주소와 `cases`를 그 사이트 자료에 맞춘다. 같은 제목의 다른 게시판 글이 정답으로 계산되지 않도록 `bo_table`이나 `id`도 지정할 수 있다. 실제로 정답 자료가 존재하며 공개되어 있는지 먼저 확인한다. 본문 전체나 개인정보가 들어간 질문을 공개 정답표에 넣지 않는다.

## 2. 공개 HTTP 검색 측정

프로젝트 루트에서 실행한다. 추가 패키지는 필요 없다.

```bash
python scripts/assess_search.py --repeats 2 --output ../local-notes/search-assessment.json
```

- 각 질문의 최초 측정과 반복 측정을 나누어 저장한다. 최초 측정이 실제 서버리스 콜드 스타트였다고 보장하지 않으며 `cold_start_verified=false`를 명시한다.
- 사이트별 요청 시작 간격은 기본 2초다. 기본 검색 제한인 분당 60회를 넘기지 않도록 천천히 순서대로 실행한다. 운영 사이트에서 간격을 줄이거나 여러 프로세스를 동시에 실행하지 않는다.
- DNT 헤더를 보내 방문·검색 집계에서 제외하고 클릭 API는 호출하지 않는다. 로그인 쿠키·관리자 자격 증명을 사용하지 않는다.
- 첫 페이지 최대 20개에서 정답 순위를 확인한다. 상위 3개 안에 정답이 있으면 성공이다. 전체와 자료 종류별 성공률이 모두 80% 이상이고 오류가 없어야 종료 코드가 0이다.
- p95는 정렬한 표본의 `ceil(0.95 × 표본 수)`번째 값이다. HTTP 오류·잘못된 JSON은 별도로 집계하며 성공 지연 통계에 섞지 않는다. 표본이 적으면 p95가 최댓값에 가까워진다.
- 보고서에는 검색어 대신 문항 ID와 공개 결과의 제목·주소를 저장한다. 정답표와 보고서는 공개해도 되는 자료인지 확인한 후 공유한다.

한 사이트만 검사하려면 `--site demo` 또는 `--site handbook`을 사용한다. 자기 정답표는 `--cases 경로.json`으로 지정한다. `--repeats 0`은 최초 측정만 수행한다.

## 3. 느린 검색의 SQL 위치 찾기

해당 사이트의 DB 환경이 설정된 관리 터미널에서 실행한다. DB 비밀번호를 명령행에 넣지 않는다.

```bash
python manage.py profile_search --query "검색" --repeat 5
```

이 명령은 비회원 권한으로 검색 함수를 직접 호출한다. `wall_ms`는 검색 함수 전체 시간이고 `sql_ms`는 DB 실행 시간의 합계다. `hydrate_ms`는 현재 페이지의 요약을 만드는 단계다. 쿼리를 후보 조회·건수·공유 캐시 등으로 분류하고 긴 쿼리의 길이와 구조 해시를 표시한다. 원문·요약·원시 SQL·DB 접속 정보는 출력하지 않는다.

이 값은 브라우저 왕복, Django 초기화, 미들웨어, 응답 직렬화를 포함하는 HTTP 측정값과 다르다. 첫 호출과 이후 호출을 구분한다. 원본 게시글·상품·권한을 수정하거나 재색인하지 않으며, 일반 검색과 마찬가지로 공유 캐시가 갱신될 수 있다. 자료 종류를 좁히려면 `--type product` 등을 지정한다.

## 4. 권한은 격리된 테스트 DB에서 확인

```bash
python manage.py test gnu_jango.site_search gnu_jango.core.test_search_preview gnu_jango.core.test_shop_board_search
```

운영 환경 변수와 분리된 테스트 DB를 사용한다. SQLite와 PostgreSQL을 각각 검사하면 두 검색 경로를 확인할 수 있다. PostgreSQL 테스트 계정에는 테스트 DB 생성 권한이 필요하다.

`SearchPermissionMatrixTests`는 비회원·일반회원·작성자·관리자의 제목·건수·요약을 비교한다. 비밀·유료 본문에는 제목과 겹치지 않는 고유 표식을 사용한다. 제목에도 있는 단어로 검사하면 정상적인 제목 검색을 본문 유출로 오해할 수 있다. 권한 철회 후 요약 조회, 활성 전의 새 세대 노출, 일부 종류만 세대 색인인 경우의 호환 경로도 확인한다.

## 반영 순서

이번 점수·조회 개선은 새 마이그레이션이나 재색인이 필요하지 않다. 검증한 코드를 배포하고 공개 HTTP 정답표를 다시 실행해 비교한다. DB에 저장된 핸드북 본문은 소스 배포로 자동 덮어쓰지 않으므로, 「검색 순위와 클릭 기록 관리」 장도 편집 내용을 보존하며 별도로 갱신한다. 전체 샘플의 `--refresh`를 무작정 실행하지 않는다.
